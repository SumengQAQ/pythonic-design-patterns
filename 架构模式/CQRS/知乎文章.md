# Python + SQLModel 实现 CQRS 模式：从零搭建订单系统

## 前言

CQRS（Command Query Responsibility Segregation，命令查询职责分离）的核心思想很简单：**写数据和读数据用不同的模型。**

不是读写分离（那是数据库层面的），而是**模型层面**的分离。写的时候用范式化的实体模型，读的时候用反范式的查询模型。

本文用 Python 3.12 + SQLModel + SQLite 实现一个最小订单系统，展示 CQRS 的标准结构。

---

## 为什么需要 CQRS？

看一个传统 CRUD 的问题：

```python
# 传统做法：读写用同一个模型
class Order(SQLModel, table=True):
    items: list[Item] = Relationship(...)

# 查订单详情
order = session.get(Order, 1)
for item in order.items:  # 触发懒加载查询
    print(item.name, item.price)
```

写入的时候我们需要 `Relationship`、`JOIN`、外键约束来保证数据一致性。但读的时候这些全是开销——你只是想把订单展示出来而已。

CQRS 的做法：

```python
# Command 写模型：范式化、关系映射
class Order(SQLModel, table=True):
    id: int = Field(default=None, primary_key=True)
    items: list[Item] = Relationship(...)

# Query 读模型：反范式、宽表、冗余字段
class OrderDetail(SQLModel, table=True):
    order_id: int = Field(primary_key=True)
    items: list[dict] = Field(sa_column=Column(JSON))
    total_item_price: Decimal = ...
    average_item_price: Decimal = ...
```

读的时候直接一条 SQL 全取出来，不 JOIN、不懒加载。

## 第一步：Command 模型（写）

```python
# command/model.py
class Item(SQLModel, table=True):
    id: int = Field(default=None, primary_key=True)
    name: str = Field(unique=True)
    price: Decimal
    count: int = Field(default=1)
    orders: list["Order"] = Relationship(
        back_populates="items", link_model=ItemOrderLink
    )


class Order(SQLModel, table=True):
    id: int = Field(default=None, primary_key=True)
    items: list[Item] = Relationship(
        back_populates="orders", link_model=ItemOrderLink
    )
    created_at: datetime = Field(default_factory=datetime.now)
```

Command 模型使用标准的 ORM 关系映射：`Item` 和 `Order` 通过中间表 `ItemOrderLink` 建立多对多关联。写入时，通过关系操作维护数据一致性。

### CommandRepository

```python
# command/handler.py
class CommandRepository:
    def __init__(self, session: Session):
        self.session = session

    def save_item(self, item: Item):
        self.session.add(item)

    def get_item_by_name(self, name: str) -> Item | None:
        return self.session.exec(
            select(Item).where(Item.name == name)
        ).first()

    def save_order(self, order: Order):
        self.session.add(order)

    def get_order_by_id(self, order_id: int) -> Order | None:
        return self.session.get(Order, order_id)
```

Repository 只是对 Session 操作的封装，方便后续替换数据源或加缓存。

## 第二步：Query 模型（读）

```python
# query/model.py
class OrderDetail(SQLModel, table=True):
    order_id: int = Field(primary_key=True)
    items: list[dict] = Field(default_factory=list, sa_column=Column(JSON))
    created_at: datetime = Field(default_factory=datetime.now)
    total_item_count: int = Field(default=0)
    total_item_price: Decimal = Field(default_factory=Decimal)
    average_item_price: Decimal = Field(default_factory=Decimal)
```

这是 CQRS 的关键：**读模型和写模型完全独立。**

- `items` 存为 JSON 列，把商品信息反范式化冗余进来
- `total_item_price`、`average_item_price` 是预计算的聚合字段
- 读取时一条 SQL 就能拿到所有需要展示的数据

### QueryRepository

```python
# query/handler.py
class QueryRepository:
    def __init__(self, session: Session):
        self.session = session

    def save_order_detail(self, order_detail: OrderDetail):
        self.session.add(order_detail)

    def get_order_detail_by_id(self, id: int) -> OrderDetail | None:
        return self.session.get(OrderDetail, id)
```

## 第三步：事件总线

Command 和 Query 之间通过事件解耦：

```python
# event_bus.py
class EventBus:
    _events: dict[str, list[Callable]] = defaultdict(list)

    @classmethod
    def register(cls, event: type[BaseEvent], func: Callable):
        cls._events[event.__name__].append(func)

    @classmethod
    def emit(cls, event: BaseEvent):
        for func in cls._events[type(event).__name__]:
            func(event)


class BaseEvent:
    @classmethod
    def register(cls, func):
        EventBus.register(cls, func)
        return func
```

目前的事件总线是**同步进程内**的。理论上应该异步化（消息队列、Redis Stream 等），但核心机制一致：Command 写完后发布事件，Query 监听事件后更新读模型。

## 第四步：事件驱动的读模型更新

### Command 端：写完后发布事件

```python
# Order 向订单添加商品
@staticmethod
def add_item(order: "Order", item: Item) -> "Order":
    with UnitOfWork() as uow:
        order.items.append(item)
        uow.command.save_order(order)

    EventBus.emit(AddedItemsToOrderEvent(order.id, item))
    return order
```

注意事件里携带的是**增量数据**（新增的 item），不是全量数据。增量更新有几个好处：

- 避免重新计算整个 Order 的开销
- 减少事件的体积
- 支持高频率增量更新

### Query 端：监听事件，增量更新

```python
# OrderDetail 监听事件
@staticmethod
@AddedItemsToOrderEvent.register
def update(event: AddedItemsToOrderEvent):
    with UnitOfWork() as uow:
        order_detail = uow.query.get_order_detail_by_id(event.order_id)
        if not order_detail:
            order_detail = OrderDetail(order_id=event.order_id)

        order_detail.items.append(event.item.to_dict())
        order_detail.total_item_count += event.item.count
        order_detail.total_item_price += event.item.price * event.item.count
        order_detail.average_item_price = (
            order_detail.total_item_price / order_detail.total_item_count
        )
        uow.query.save_order_detail(order_detail)
```

### 关于一致性

这个实现中，Command 和 Query 共享同一个 UoW 的事务，所以实际上是**强一致**的。如果追求**最终一致性**，需要将事件发布和事务分离——事务提交后将事件推入独立的队列，由另一个进程异步消费。这会在写完后到读模型更新之间产生一个短暂的延迟窗口。

## 第五步：Unit of Work

```python
class UnitOfWork:
    def __init__(self, engine: Engine):
        self.engine = engine

    def __enter__(self):
        self.session = Session(bind=self.engine, expire_on_commit=False)
        return self

    @property
    def command(self) -> CommandRepository:
        return CommandRepository(session=self.session)

    @property
    def query(self) -> QueryRepository:
        return QueryRepository(session=self.session)

    def __exit__(self, exc_type, exc_val, exc_tb):
        if exc_type:
            self.session.rollback()
        else:
            self.session.commit()
        self.session.close()
```

UoW 通过上下文管理器统一管理事务的生命周期。Command 和 Query 的 Repository 共享同一个 session，保证数据的一致性。

### expire_on_commit=False

这个小参数解决了新手最常见的问题：ORM 对象在 commit 后属性被过期（expire），session 关闭后无法访问。设置为 False 后，commit 后属性值保留在内存中，可以正常读取。

## 完整流程

```python
# 1. 初始化商品库存
Item.create_and_restock(name='coffee', price=Decimal(15), count=12)
Item.create_and_restock(name='water', price=Decimal(3), count=5)

# 2. 创建订单
order = Order.create([
    Item.get_by_name('coffee', need=5),
    Item.get_by_name('water', need=3),
])

# 3. 查看订单详情（Query 模型）
detail = OrderDetail.get_by_id(order.id)
print(detail.total_item_price)   # 84
print(detail.items)              # [{"name": "coffee", ...}, {"name": "water", ...}]
```

## 遗留问题和后续方向

| 问题 | 说明 | 改进方向 |
|------|------|---------|
| 事件总线同步 | 当前 EventBus 是进程内同步调用 | 改为消息队列（Redis Stream / RabbitMQ） |
| 一致性模型 | 共享事务，实际上是强一致 | 事务提交 → 发布事件 → 异步消费 → 最终一致 |
| 事件持久化 | 服务重启后事件丢失 | 持久化事件存储 + 重试机制 |
| 业务与 ORM 耦合 | `Item.get_by_name` 直接操作 Repository | 引入 Service 层隔离 |
| 缺少 Saga | 订单创建涉及扣库存、加订单，未做补偿 | 引入 Saga 模式，失败时自动回滚 |

## 总结

本文实现了一个最小 CQRS 订单系统，覆盖了以下核心概念：

- **命令模型 vs 查询模型**：写用范式化的 ORM 关联，读用反范式的 JSON 宽表
- **事件驱动的读模型更新**：Command 写完后发事件，Query 监听后增量更新
- **Unit of Work**：统一管理事务和 Repository 依赖注入

以上代码在 Python 3.12 + SQLModel 下运行通过，完整源码见 GitHub。
